# ST0002 WP01: the install and release design, settled

dc's record for WP01 (AC-01.1), 2026-11-02. It checks the T1 to T10 table and E1 to E8 in `design.md` against what Intent and devbin 0.1.19 actually do, and settles the layout with ST0001 WP02. vc accepted its amendments to `design.md` (section 7), and hv ruled on its three open points (section 6; recorded in 5574e38 as ST0002 design rulings 5 to 7 and ST0001 design 3.4). Unprefixed paths are in Intent's `bin/.devbin/`.

## 2. The install layout (the seam with ST0001 WP02)

- **A tree** is a root holding:
  - `bin/pplr`;
  - `bin/pplr-contacts` (macOS only);
  - `Pplr Links.app` (macOS only; section 4);
  - the manifest `.pplr-install`.
- **The brew root** is `$(brew --prefix)/opt/pplr/libexec`, and only `bin/pplr` is linked into `$(brew --prefix)/bin`. Opt is a prefix the maintainer names; dev is the checkout, with the binaries in `target/<profile>/`.
- **One function** in `config.rs` (or `install.rs`, if WP03 splits it out) resolves the running binary with `std::env::current_exe` and canonicalises it. It returns the tree's root and kind (brew, opt, dev or unknown), and the paths of the sidecar and the app inside that root. Everything else asks it: the fallback, the Contacts store, `handler`, doctor, `install` and the version line.
- **Dev is recognised** by the root holding `Cargo.toml` with `name = "pplr"`. The sidecar's dev path is `target/<profile>/pplr-contacts`, built by devbin's build step, never at run time.
- **The runtime set** is one list beside that function: `bin/pplr`, plus `bin/pplr-contacts` and `Pplr Links.app` on macOS. `install`, the manifest and doctor all read it.
  - Its **dirty inputs** are cargo's dep-info (`target/<profile>/pplr.d`) plus `swift/pplr-contacts/main.swift` and the handler app's source.
- **The manifest** is in T3's form, header first:
  - `# tool: pplr`
  - `# version`
  - `# source_commit` (the full sha)
  - `# managed_by: pplr|brew`
  - then one `shasum -a 256 -c` line per runtime file, sorted by `LC_ALL=C sort`.
  - The `.app` is a directory, so its files are listed one per line, in the same sort.

## 3. Signing (WP07)

- **Identity**: "Developer ID Application: Geodica Pty Ltd (76BQL8L47U)".
- **Designated requirement** for each binary: `identifier "<id>" and anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.6] and certificate leaf[field.1.2.840.113635.100.6.1.13] and certificate leaf[subject.OU] = "76BQL8L47U"`. This is the form codesign derives for a Developer ID signature, written down so verification does not depend on the binary's own claim.
- **Embedded Info.plist**: `pplr-contacts` gets one at link time (`swiftc ... -Xlinker -sectcreate -Xlinker __TEXT -Xlinker __info_plist -Xlinker <plist>`), carrying `CFBundleIdentifier` and `NSContactsUsageDescription`, so macOS can show the access prompt for a bare binary.
- **Notarisation**: the signed binaries are zipped and submitted with `notarytool submit --wait`, then each is checked on a quarantined copy. Bare binaries cannot be stapled, so first use needs Gatekeeper's online check, as with Intent.
- **AppleScript writes**: `pplr` runs `/usr/bin/osascript`, which sends the Apple Events, so pplr needs no automation entitlement. WP06 records which process macOS asks about.

## 4. The handler app

Ruling 1 signs every binary, and only rhadamanth holds the identity. So `Pplr Links.app` can no longer be compiled and ad-hoc signed by `pplr handler --install` on the user's machine.

- **Settled** (hv, 6.3):
  - The app is built and signed at release (with devbin's core `.app` signer, the `macos.*` keys), and ships in the runtime set.
  - Its script runs the `bin/pplr` beside it, found through `path to me`, so one signed app works in any tree. Nothing about the tree is baked into it.
  - `pplr handler --install` then only registers the tree's app with `lsregister`, and `--uninstall` unregisters it.
- This replaces design 3.4's "the app runs the opt link": the app sits in the opt tree and names nothing.
- It is ST0001 WP08's to build, with the release steps in WP07.

## 5. The release order

Under devbin's release core, with `release.assets.workflow: release-assets.yml`:

1. **Local:** `bin/devbin release`, after the gates `check all`, `test all` and `doctor`, the kovacs leg and CI on `candidate/<tag>`. It bumps through `tools/lock-sync` (E4), commits, tags, pushes `local` then `upstream`, and creates the GitHub release.
2. **CI:** the tag push starts `release-assets.yml`, which builds and attaches the two Linux musl tarballs.
3. **Local:**
   - `bin/devbin macos prepare` builds the macOS target, signs `pplr`, `pplr-contacts` and the app, notarises them and verifies them.
   - It packs the target's tarball (`bin/` and the app), and refuses to pack an unsigned or un-notarised binary (AC-07.2).
4. **Local:** `bin/devbin release attach v<version> --from dist/macos` waits for step 2, attaches the macOS tarball and writes `SHA256SUMS` over every asset.
5. **Local:** `bin/devbin formula publish` (the release's `after:`) renders `packaging/homebrew/pplr.rb` from the version and `SHA256SUMS`, and pushes the tap.

Each asset is one tarball per target, holding the tree's runtime set apart from the manifest. The formula runs `libexec.install Dir["*"]`, sets 0755, writes the manifest, verifies with `-R` and links `bin/pplr`.

## 6. hv's rulings, 2026-11-02

1. **Targets**: Intent's set, `aarch64-apple-darwin` plus Linux `x86_64` and `aarch64` musl. There is no x86_64 macOS target.
2. **Notary credentials**: one neutral set, `geodica.apple.{APPLE_ID,APPLE_APP_PASSWORD,APPLE_TEAM_ID}` in the login keychain. The entries are hv's to create; pplr's signer references the names and creates nothing.
3. **The handler app** ships prebuilt and signed in the tree, and `handler --install` only registers it (section 4).

## 7. Amendments to design.md, accepted by vc

- **E1**: targets per 6.1.
- **E2**:
  - explicit identifiers;
  - `-R` with the designated requirement in section 3;
  - the addressbook entitlement and the embedded Info.plist for `pplr-contacts`;
  - a host guard that refuses on CI and without the identity;
  - notary credentials from `geodica.apple.*` (6.2).
- **T8 and E3**:
  - the formula comes from devbin's `formula` (assets mode), not Intent's `brew.lib`;
  - the order is section 5;
  - `release-assets.yml` builds Linux only.
- **T1 and design 3.4**: the tree holds `Pplr Links.app` on macOS, and `handler --install` registers it (section 4).
- **Unchanged**: T2 to T7, T9, T10, E4 to E8.
