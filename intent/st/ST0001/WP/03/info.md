# WP-03: Golden capture from the legacy code

## Objective

Capture the exact output of every command that writes or reports, from the legacy implementation over a synthetic People tree, as goldens the Rust binary must reproduce byte for byte.

**Scope**

- **A synthetic fixture tree** with no real person's data, built by a script or committed as data. It covers the edge cases in design section 4, step 2, and includes a Contacts dump JSON.
- **A capture driver** in zsh (eg `tests/golden/`; nothing Python is committed). It runs each writing and reporting command under the legacy code with `PPLR_TODAY` pinned and the environment sandboxed, and records per scenario the stdout, stderr, exit code and resulting tree (every file's bytes).
- **Scenarios** cover at least:
  - `new`, `json`, `index`, `reindex`, `count`, `meetings`, `grep`, `refresh`, `pictures`;
  - `tag` and every `tags` and `contact` subcommand;
  - `email`, with a fake `mail-recent`;
  - `rename`, including a refs directory reached through a symlink;
  - `links`, covering paths, CMS URLs and a symlinked note;
  - `resolve` and `open --print`;
  - every `sync` mode against the JSON store, including `--plan --json` and the workbook's cell contents.
- **Time-dependent fields** (eg `generated_at` in `tags_index.json`) are listed in the goldens' README, each with how the replay treats it. That list is the "time-dependent fields" exception named in AC-00.4.
- **A replay test** in `tests/cli.rs` runs every golden against the Rust binary and fails on any byte difference. It skips only the commands still on the fallback, read from the command table, so each port WP turns its goldens on. It lands on WP02's scaffold; the capture itself needs no Rust.
- The capture runs the legacy Python once, as an oracle.

**Criteria**: AC-03.1.

**Order**: before any WP deletes a legacy command (design section 6, rule 3).
